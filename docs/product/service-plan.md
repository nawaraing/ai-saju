# AI 사주 서비스 기획서 (Service Plan)

> 대화형 AI 사주 서비스의 제품 기획 문서.
> 기술 구현은 `architecture.md`, 명리학 지식은 `domain-knowledge.md`,
> 해석 프롬프트는 `interpretation-prompt.md` 참고.
> 이 문서는 "왜/무엇을(What & Why)"을 다룬다. "어떻게(How)"는 기술설계서로.

---

## 1. 서비스 개요 · 문제 정의

### 배경
기존 사주 서비스는 두 갈래로 나뉘고, 각각 한계가 뚜렷하다.

- **전통 사주 앱**: 여덟 글자 계산은 정확하지만, 해석이 정해진 문구 조합이라 천편일률적이고 딱딱하다.
- **범용 챗봇에 사주 요청**: 대화는 자연스럽지만, 여덟 글자 계산부터 틀린다(환각). 절기·윤달·시주 환산을 LLM이 정확히 못 한다.

### 포지셔닝
본 서비스는 이 둘 사이에 선다.

> **"계산은 정확하게(코드), 해석은 자연스럽게(LLM)"를 결합한 대화형 사주 서비스.**

- 사주 여덟 글자·오행·용신 등은 **검증된 계산 엔진**이 결정론적으로 산출한다.
- 그 결과를 **LLM이 상담사처럼** 자연어로 풀이한다.
- 계산과 해석의 역할을 명확히 분리해, 정확성과 대화 경험을 동시에 확보한다.

## 2. 타깃 사용자

- **주 타깃**: 명리학을 공부하려는 전문가가 아니라, 자기 삶의 고민을 가볍게 물어보고 싶은 일반인.
- 전문 용어(십신·용신 등)를 몰라도 "올해 연애운 어때?" 수준의 질문으로 답을 얻을 수 있어야 한다.
- **접속 환경**: 가볍게 폰으로 보는 경우가 대부분 → **모바일 우선**.

### 페르소나 예시
- 20~30대, 연애·취업·이직 같은 현실 고민을 안고 있음.
- 진지한 역술 상담(고비용)까지는 부담스럽고, 가볍고 재미있게 확인하고 싶음.
- 결과를 캡처해 친구와 공유하거나 궁합을 같이 보고 싶어함.

## 3. 핵심 기능

계산 엔진이 지원하는 기능 후보(참고: `saju-fortune` 패키지 / MCP 도구 모델).

| 기능 | 설명 | MVP 포함 |
|------|------|:---:|
| 종합 사주 풀이 | 여덟 글자·오행 분포·전반적 성향 | ✅ |
| 올해의 운세 | 특정 연도 세운 기반 풀이 | ✅ |
| 주제별 운세 | 연애 / 재물 / 직업 / 건강 | △ (일부) |
| 대운 흐름 | 10년 단위 인생 흐름 | ❌ (확장) |
| 오늘의 운세 | 일운 | ❌ (확장) |
| 궁합 | 두 사람 간 관계 풀이 | ❌ (확장) |

### MVP 범위 (1차 출시)
- **"종합 풀이 + 올해 운세"** 하나를 제대로 만드는 데 집중한다.
- 이유: 기능이 늘수록 프롬프트 품질 관리와 검증 부담이 커진다. 대화 경험의 완성도를 먼저 확보한다.
- 궁합·오늘의운세·대운은 검증 후 단계적으로 확장한다.

## 4. 차별점 (핵심)

> ⚠️ 계산 엔진(`saju-fortune` 등)은 누구나 설치할 수 있다.
> 계산 결과 자체로는 차별화가 불가능하다. 차별점은 아래 세 곳에서만 나온다.

### 4-1. 해석의 톤과 관점
- 같은 여덟 글자를 어떤 태도로 풀지가 서비스의 색깔.
- `domain-knowledge.md` 0장에서 정할 **채택 유파 + 말투**와 직결.
- 후보: 따뜻한 공감형 / 냉철한 분석형 / 친근한 반말형 등 — **결정 필요**.

### 4-2. 대화 경험 (UX)
- 결과를 한꺼번에 쏟아내지 않고, 상담사처럼 **인터뷰하며** 풀어주는 대화형 경험.
- 필요한 정보를 되묻고, 사용자가 고른 주제만 깊게 파고든다.

### 4-3. 타깃 집중 (선택 전략)
- 종합 사주 앱은 이미 포화. 좁게 파는 것도 전략.
- 예: 취준생 직업운 특화, 커플 궁합 특화 등.

## 5. 사용자 플로우

```
[입력]
 1. 양력/음력 선택
 2. (음력이면) 평달/윤달 선택
 3. 생년월일 (YYYY-MM-DD)
 4. 태어난 시각 (모르면 → 시주 미확정, 연·월·일 중심 보수적 풀이)
 5. 성별 (대운 방향 계산에 필수)
 6. (선택) 출생 시군구 — 진태양시 보정
 7. 보고 싶은 주제 선택
      ↓
[계산]  서버가 계산 엔진 실행 → 여덟 글자·오행·십신·신강신약·용신 산출
      ↓
[해석]  계산 결과 + 해석 프롬프트 → LLM → 자연어 풀이
      ↓
[결과]  구조화된 풀이 표시 (요약 → 오행 분포 → 주제별 → 실천 조언 → 주의 문구)
```

- 결과 화면은 공유(캡처)를 염두에 두고 디자인한다.

## 6. 톤 & 운영 정책

> 계산 엔진 스킬의 "When not to use / Notes / Failure modes"를 서비스 정책으로 채택.

### 해석 태도
- 결정론적 예언이 아니라 **자기 이해·자기 점검용 참고 자료**로 제시한다.
- 단정하지 않고 경향으로 말한다("~한 경향이 있어요").
- 단점은 반드시 **보완책과 함께** 제시한다.

### 금지 사항
- 단정적 흉언, 저주, 사망 예언, 질병 확정 표현 금지.
- 의료·투자·법률 판단을 대신하지 않는다(면책 문구 노출).
- 궁합 결과를 이별/결혼 결정의 근거로 제시하지 않는다.

### 개인정보 정책
- 입력한 생년월일시는 **민감정보**로 취급한다.
- 원칙: 풀이 중에만 사용하고 영구 저장하지 않는다.
- 다만 계산 결과(사주 간지·오행 분포 등 파생값)는 통계 목적으로 로그인 없이 익명 저장한다.
  저장 범위와 보호 방식은 `architecture.md` §6, `database.md` 참고.

## 7. 비기능 요구사항 (품질 요구)

> "무슨 기능"이 아니라 "어떻게 동작해야 하는가". 구현 방법은 `architecture.md`.

- **반응형 웹**: 모바일 우선(mobile-first). 주 사용자가 모바일이므로 폰에서 최적, PC·태블릿에서도 레이아웃이 깨지지 않아야 한다.
- **응답 속도**: LLM 호출로 지연이 생기므로, 계산 결과는 즉시 보여주고 해석은 스트리밍/로딩 처리로 체감 대기를 줄인다.
- **보안**: LLM API 키는 서버에서만 접근(클라이언트 노출 금지). 계산·LLM 호출은 서버 측에서만 수행.
- **안정성**: 계산 엔진 실패, 태어난 시간 누락, 음력 변환 실패 등 예외 상황에서 사용자에게 명확한 안내.

## 8. 수익 모델 (검토)

> 스킬이 다루지 않는 순수 사업 판단 영역. 아래는 후보.

- 무료 기본 풀이 + **상세 리포트 유료**
- **주제별 건당 결제** (연애운·궁합 등)
- **구독형** (오늘의 운세 매일 제공 등)

### 원가 고려
- LLM API는 호출마다 비용 발생 → 사용자 1인 풀이당 LLM 비용이 **가격의 하한선**.
- 무료 제공 범위는 원가와 함께 설계해야 지속 가능.

## 9. 리스크

> 계산 엔진 스킬의 Failure modes에서 도출.

| 리스크 | 내용 | 대응 방향 |
|--------|------|-----------|
| 태어난 시간 미상 | 시주 확정 불가 → 풀이 품질 저하 | 시간 모름 플로우 별도 설계, 한계 명시 |
| 음력·윤달 변환 | 변환 오류 시 사주 전체가 틀림 | 검증된 만세력/라이브러리, 윤달 플래그 필수 |
| 패키지 신뢰성 | 남의 계산 패키지에 의존 | 검증 케이스로 정확도 확인 후 채택 |
| 보안 감사 경고 | 패키지에 Warn 표시 존재 | 도입 전 감사 내용 확인 |
| LLM 해석 품질 편차 | 답변이 들쭉날쭉 | 프롬프트 구조화, 출력 형식 고정 |
| 개인정보 | 민감정보 취급 | 저장 최소화, 명확한 고지 |
